# Changelog

All notable changes to `rhizodb` are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html). A released section's heading is exactly `## <version>`, such as `## 0.1.0`, because the release workflow reads it as the release notes.

## Unreleased

### Changed

- Relationship chunks store their relationships in columns, which packs each type, source, target, and integer property in the fewest bits its chunk needs, so a graph's relationships take less than half the bytes they took. The graph format is now 16, and opening a database of an older graph format as its writer rewrites every relationship chunk in columns in the upgrade's commits of bounded size. 0.2.1 and earlier then refuse the file with `ErrorKind::UnsupportedFormatVersion`, so back it up with 0.2.1 first, and go back to 0.2.1 through `Database::export` and `Database::import`.
- A read-only open now creates a side file named after the database file with `-shm` and maps it, so the processes that have the file open read-only form a session that a later change lets a writer join. The last of them to close removes the side file. A read-only open of 0.2.0 or 0.2.1 refuses a file while a session holds it, or after a process of one crashed until the next open removes its side file. Where the directory refuses to create the side file, as on read-only media, or on a file system that is not local, a read-only open reads the file alone, as in 0.2.1, and it leaves no side file. The side file takes the database file's permissions. A process opens a file read-only at most once, now through any of its paths and hard links.
- A `MATCH` of one directed relationship, such as `MATCH (:Person)-[k:KNOWS]->(:Person) RETURN count(*), sum(k.since)`, that feeds `count`, `sum`, `avg`, `min`, or `max` of the relationship's properties without grouping keys now reads the relationships in the order they are stored instead of one at a time from each start node. On a graph of 200,000 relationships that query takes about a twentieth of its time before. Results do not change, and only a damaged file can fail differently, since such a query reads every relationship chunk and no adjacency: a value whose result could depend on the order of the rows, such as a float or an integer sum that could overflow, makes the query run as before.

### Added

- `OpenOptions::multi_process`: several processes can open one database file for writing with it, beside any number of read-only processes. A write transaction in any process waits for one in another, as it waits for another thread's today, and begins on the newest commit of every process. Each process reads every commit of every other process made before each of its reads begins, and catches up and adopts the checkpoints of the others from a thread of its own while idle, so it never keeps the file from reusing space for long, and no checkpoint in one process reuses space another process still reads. A process that dies loses no commit it reported: the next writer goes on from the last published one. A writer that closes while other processes have the file open leaves its log to them, and it keeps the log after a checkpoint that another process pins for a snapshot. It needs a local file system with byte-range locks and shared mappings.
- `ErrorKind::TooManyProcesses`: an open found every slot of the file's multi-process session taken.

## 0.2.1

Released on 2026-11-28.

Fixes for opens through symlinks and hard links, for `Database::apply` on a writer, and for `rand()` inside aggregates, and a cap on the dump lines that an import reads. The file format does not change.

### Upgrading from 0.2.0

- If a database was last opened through a symlink to its file and was not closed cleanly, make the first open after upgrading go through that same symlink, and not read-only. That open moves the log segments that 0.2.0 named after the symlink beside the file, as the entry under Fixed describes. An open through the real path fails with `ErrorKind::CorruptData` until then, and nothing is lost.
- On Unix an open of a database file with more than one hard link now fails with `ErrorKind::Storage`. Copy the file instead of linking it, or remove the extra link.
- On Windows an open that is not read-only now fails on a volume that does not support `GetFinalPathNameByHandle`, as the entry under Fixed describes.

### Added

- `OpenOptions::max_dump_line_bytes` caps the bytes of one dump line that `Database::import` reads. A longer line fails with `ErrorKind::InvalidDump` once that many bytes are read, so a host that imports dumps it did not write can bound the memory one line takes. No cap is set by default.

### Fixed

- Opening a database through a symlink to its file, or through a second hard link, looked for the write-ahead log segments and staging file beside that path and under its name instead of beside the file itself. After an unclean shutdown, an open through another path then failed with `ErrorKind::CorruptData` (write-ahead log missing) although every commit sat in segments named after the first path, and two read-only opens in one process through two hard links both succeeded. An open now follows every symlink and `..` in the path once and names every side file after the file it reaches, so every path to a file finds one log and counts as one open. On Unix an open of a file with more than one hard link now fails with `ErrorKind::Storage`, since each name would find its own log, so copy a database file instead of linking it.
- A database that 0.2.0 or earlier left after an unclean shutdown, opened through a symlink to its file, kept its log beside the symlink under the symlink's name. The first open through that same path that is not read-only now moves those segments beside the file. It holds the file's lock throughout, and first replays the moved segments with any already beside the file as a read-only open would. If that replay fails, or the segments beside the file do not exactly continue the ones being moved, it moves nothing and fails with `ErrorKind::Storage`, naming the segment files. It moves the newest segment first and syncs both directories after each move, so a crash mid-move leaves the file without the start of its log: an open through the real path then fails with `ErrorKind::CorruptData` instead of reading part of the log, and the next open through the symlink finishes the move. A file system without file locks refuses the move, and a read-only open fails with `ErrorKind::ReadOnly` while the move is due. Only the exact path the crashed process used finds those segments, not the real path and not another link in a chain of symlinks, so make the first open after upgrading go through that path. If a segment cannot be renamed, for example because the symlink and the file are on different file systems, copy it beside the file under the file's name and remove the original.
- An open through a symlink whose target does not exist yet replaced the symlink with a new regular file. It now creates the database file at the symlink's target and keeps the symlink.
- On Windows a database path is now resolved with `GetFinalPathNameByHandle`, which some volumes, such as some RAM disks and network or virtual drives, do not support, so an open that is not read-only on such a volume now fails where it used to work, as a read-only open already did. Error messages there may show the path in its `\\?\` form.
- `Database::apply` on a writer or a fenced writer could leave it refusing reads and writes with `ErrorKind::FormatUpgradePending`. This happened when the changes carried an older graph format or an upgrade, as a new writer's first changes after a rolling upgrade do. The apply failed with `ErrorKind::NotReplica` or `ErrorKind::WriteTransactionOnThisThread` but still marked the graph as waiting for an upgrade. The mark stayed when the call came from a thread holding a write transaction, until the next apply or promote, and otherwise cleared once the call returned. Only a replica now starts waiting for an upgrade.
- An aggregate argument that called `rand()` only inside a pattern's property map or the clauses of a subquery was accepted, as in `sum(VALUE { RETURN rand() })` or `count(EXISTS { MATCH (n)-->(m) WHERE rand() < 0.5 })`, and returned a random result. It now fails with `ErrorKind::NonConstantExpression`, as `rand()` directly in the argument does.

## 0.2.0

Released on 2026-11-28.

Embedded replication, read-only opens from many processes, bounded memory for large queries and file upgrades, and checksummed relationship chunks. The file format changes, so read Upgrading from 0.1.x before upgrading.

### Upgrading from 0.1.x

- The file format changes, and the change cannot be undone. This release writes engine format 1.4, which adds the replication history, the role, and the log kept for peers, and graph format 15, whose relationship chunks carry a checksum. Any open that is not read-only records engine minor 4 before it reads the graph, even one that only runs read queries, opens a replica, or then fails with an error, and opening a database of graph format 11 to 14 as its writer rewrites every relationship chunk with its checksum. 0.1.x then refuses the file with `ErrorKind::UnsupportedFormatVersion`.
- Back up each database with 0.1.x before upgrading, with `Database::backup_to` or by copying the closed file. To go back to 0.1.x after upgrading, export with this release's `Database::export` and import into 0.1.x with `Database::import`. The dump format stays at version 1, and 0.1.x reads a dump that this release writes.
- A read-only open never upgrades, so it fails with `ErrorKind::ReadOnly` on a file that 0.1.x wrote until one writer open of this release has upgraded it.
- The limits on a value that a query builds, 10,000,000 list items and map entries and 256 MiB of strings, now count through every nested list and map, where 0.1.0 counted each list or string alone. A query whose nested values pass them now fails with `ErrorKind::NumberOutOfRange`, and `OpenOptions::max_value_items` and `OpenOptions::max_value_bytes` raise them.
- An `Error` no longer repeats its cause in its message, as the entry under Changed describes, so a host that matches on message text or walks the `source` chain sees different text.
- `Database::backup_to` on a file system without hard links can now fail with `ErrorKind::Storage` where 0.1.x renamed the copy into place, as the entry under Changed describes.
- No public item is removed or changed. The new `ErrorKind` variants need no change to a host's `match`, since `ErrorKind` is `#[non_exhaustive]`.

### Added

- `OpenOptions::read_only` opens an existing database file under a shared lock, so any number of processes read one file at once while no process writes it, and an open that writes fails with `DatabaseAlreadyOpen` until they close it. A read-only open never creates, writes, renames, or removes a file: it replays the log of an unclean shutdown into memory, upgrades nothing, and runs no checkpoint. Writes, index changes, imports, compaction, and the replication calls that write fail with the new `ErrorKind::ReadOnly`, and so does opening a file whose graph format or tokenizer needs an upgrade. A read-only open also fails with `DatabaseAlreadyOpen` while a `-shm` file lies beside the database file or while the same process holds the file open read-only. After an unclean shutdown it syncs the log it replayed before any read, and on Windows, which syncs only through a handle with write access, it fails with `ReadOnly` instead. `Database::snapshot` of a read-only database whose last checkpoint a crash cut between its stages fails with `ReadOnly` too, and `Database::role` reports the role the file records.
- Embedded replication. `Database::changes_since` returns the whole transactions after another database's `Database::position` as `Changes`, which travel as checksummed bytes and `Database::apply` logs on a replica, and replicas relay changes to further replicas. A `Position` holds a term, a writer id, an LSN, a chain hash over the history, and the id of the database the history belongs to, so two histories that reuse a term are told apart and a replica never follows an unrelated database.
- `Database::promote` makes a node the writer of a higher term, and `Database::demote` hands writing over without losing a write, waiting a given time for an open write transaction. A file remembers its role, which `Database::role` reports as a `Role`: a writer reopens fenced until the host promotes it again, and `OpenOptions::replica` creates a replica.
- `Database::history` returns the terms a database followed as a `History`, which `Database::compare_lineage` compares with another database's to tell which side catches up and which must resync, as a `Lineage`. Each `HistoryEntry` names its term, writer id, first LSN, the last LSN once its writer stepped down, and, with `HistoryEntry::incarnation`, the database file that began the term, so two files that began one term under one writer id are told apart.
- New error kinds `NotWriter`, `NotReplica`, `Fenced`, `Diverged`, `DifferentDatabase`, `TooFarBehind`, `Gap`, and `WriterBusy`, and `Error::replication_failure`, which returns the positions and LSNs behind a replication error as a `ReplicationFailure`.
- `Database::snapshot` pins the last checkpoint as a `Snapshot`, a stream of checksummed chunks read at any offset with `Snapshot::read_at`, so a transfer that is cut off resumes where it stopped. Writes, deletes, and compaction go on while it is read, and taking one forces no checkpoint.
- `Database::install_snapshot` and `OpenOptions::install_snapshot` write a snapshot stream to a database file and open it as a replica. The stream is synced and checked page by page before it replaces the file, so after a crash or a failure the path holds the old database, no database, or the whole snapshot, and a damaged chunk fails as `ErrorKind::CorruptData`.
- `Database::acknowledge` keeps the write-ahead log after a peer's `Position` for that peer, and `Database::forget_peer` releases it. `OpenOptions::max_retained_bytes`, 1 GiB by default, caps the log kept for peers and snapshots, past which the peers furthest behind are released.
- `ErrorKind::InvalidPeerId` for a peer id that is empty or longer than 64 bytes.
- Acknowledged peers and the log kept for them survive a restart: the database file records each peer's position with every checkpoint and when it closes, and a reopened database keeps the log segments those peers still need, so a restarted writer does not force its replicas to a new snapshot. After a crash each peer is kept at the position the last checkpoint recorded, and a peer first acknowledged after that checkpoint is forgotten. A database keeps the log for at most 32 peers, and acknowledging another fails with the new `ErrorKind::TooManyPeers`.
- `OpenOptions::force_install`, without which an install refuses, with `ErrorKind::Fenced`, a snapshot older in term than the database it replaces has seen, with `ErrorKind::DifferentDatabase`, a snapshot of another database than the one it replaces, and, with `ErrorKind::CorruptData`, to replace a database whose history of terms cannot be read. An installed database is a replica of a fresh incarnation that keeps the newest term either side has seen, so changes of a replaced writer are fenced.
- `OpenOptions::snapshot_time_limit`, one hour by default, after which the database releases a `Snapshot` still alive and reading it fails with the new `ErrorKind::SnapshotExpired`, and `DatabaseStats::held_bytes`, the space that open snapshots and read transactions keep the file from reusing.
- `OpenOptions::max_value_items` and `OpenOptions::max_value_bytes` set how many list items and map entries, and how many bytes of strings and byte strings, one value that a query builds may hold, counted through every nested list and map. They default to 10,000,000 items and 256 MiB, and `range()` fails with `ErrorKind::NumberOutOfRange` once it would build more than `max_value_items` elements.
- `ErrorKind::FormatUpgradePending`: a replica or fenced writer of a newer build opens a database whose graph format or keyword index tokenizer is older than its own. It refuses graph reads with this kind, naming the stored graph format and its own where the graph format differs, and writes with `NotWriter` as any replica does, while it keeps applying, serving, and relaying changes, taking snapshots and backups, and checking the file, and it serves reads once it applies its writer's upgrade or once the host promotes it, which upgrades it. A replica that receives an older format from its writer, as a new replica of a writer on an older build does, starts waiting before it applies it. A rolling upgrade restarts the replicas first, hands writing over to one of them, and restarts the old writer last.

### Changed

#### Storage, upgrades, and errors

- Opening a database of an older graph format or tokenizer as its writer upgrades it in commits of bounded size that record their progress, instead of one write transaction, so a large file upgrades within bounded memory and log records, and an upgrade cut off by a crash resumes where it stopped. While an upgrade is under way the file's format version is marked, so no build reads the half moved graph: older builds refuse the file with `ErrorKind::UnsupportedFormatVersion`, a read-only open fails with `ErrorKind::ReadOnly`, a replica waits with `ErrorKind::FormatUpgradePending`, and the next writer open of this build resumes the upgrade. The upgrade ends with one checkpoint, so a snapshot taken right after it installs on a replica instead of failing with `NotWriter`. Opening a database of the current format runs no upgrade checkpoint.
- `Database::apply` refuses, with `ErrorKind::UnsupportedFormatVersion`, a change that records a graph format newer than this build reads, after applying the changes before it, so a replica of an older build never takes a format it would misread.
- An `Error` no longer repeats a cause in both its message and its `source`, so reporters that walk the chain print each cause once. A failed procedure body, a failed dump read or write, an unreadable path, and a storage failure caused by an I/O error keep that error as the `source`, with a message that names only this failure, such as "procedure `x` failed" or "cannot open the database at …". The `std::io::Error` behind a storage failure, such as a failed open, backup, commit, or read of a snapshot stream, is now the direct `source`, except for a file lock another `Database` holds, which fails with `ErrorKind::DatabaseAlreadyOpen` and no `source`, so a host downcasts it with `error.source()?.downcast_ref::<std::io::Error>()` and reads its `io::ErrorKind`. Every other storage or graph failure has no `source`, and its message holds the whole account.
- `Database::backup_to` on a file system without hard links, such as FAT, exFAT, and some network and FUSE file systems, moves the copy into place with a rename that fails rather than replace a file, on Linux, Android, and Apple platforms. On Linux, a file system that lacks that rename, as many FUSE servers and some NFS setups do, fails the backup with `ErrorKind::Storage`. On other platforms such a backup now fails with `ErrorKind::Storage`, and the message says the file system may not support hard links, where 0.1.x renamed the copy into place and could replace a file created at the target after the check.
- A writer that lost its lease to a failover rejoins as a replica without a snapshot when it holds no change the new writer lacks: once it has heard of the new term, from `Database::changes_since` or `Database::acknowledge` with the new writer's position, `Database::demote` records no step down and the file opens as a replica, and one that holds changes the new writer lacks still fails with `ErrorKind::Diverged`. `Database::acknowledge` with a position of a newer term fences a writer. A replica that heard of a term before receiving its first change applies that change.

#### Queries and performance

- A `MATCH` pattern starts at a later node that an earlier clause binds, or that an ID lookup or a property index serves, instead of reading every node at its left end and checking the far end of each walk, so `MATCH (x:Person {id: $id}) MATCH (a)-[:FOLLOWS]->(x)` and `MATCH (a)-[:KNOWS]->(b:Person {id: $x})` with an index on `Person.id` read only the relationships of the found node. A later lookup is used only when it finds fewer nodes than the leftmost start. The rows are the same, though rows without `ORDER BY` may come in another order, and since a property map is evaluated only for the elements the walk reaches, a moved start can change whether a query raises a value error such as division by zero.
- Returning a node or a relationship reads each label, relationship type, and property key name from storage once per database (once per transaction inside a write transaction) instead of once per element, so returning many elements no longer reads storage once per label and property.
- `labels(n)`, `keys(n)`, `keys(r)`, and `type(r)` no longer decode the element's property values, so they cost the same on elements with large text or vector properties as on small ones.
- Reading or changing the relationships of a node no longer reads the stored relationships of a hub node in the same block of 16 node IDs. Before, every such read or commit read the whole of the hub's adjacency, so its cost grew with the hub's degree. A commit that adds a relationship to a hub no longer reads the hub's stored adjacency either, and rewrites it once its pending changes reach the larger of half a part and the square root of eight times its size. Adding relationships to one node one commit at a time no longer takes time quadratic in its degree, and the bytes it writes for a large hub grow with the degree to the power 1.5 instead of the square.
- A pattern's property map, as in `MATCH (a)-[:R {w: 1}]->(b {active: $flag})`, whose values are constants or parameters is evaluated once per input row instead of once per candidate element. Its keys are looked up once per query instead of once per candidate, and a relationship map reads only the properties it tests instead of decoding the whole record.
- `SET`, `REMOVE`, `DELETE`, `CREATE`, and `MERGE` keep the property columns, node labels, adjacency, and tokens they read for the rest of the query instead of starting over for every expression, so `MATCH (n) SET n.visits = coalesce(n.visits, 0) + 1` no longer loads and checks a node's label chunk on every row. Each write is still seen by every read after it.
- Adding a label a node already has, or removing one it lacks, no longer checks the node's stored labels again at every call in a write transaction.
- A single-node `MATCH` whose filter does arithmetic or `||` on the node's properties, as in `MATCH (p:Person) WHERE p.id % 4 = 0 SET p.age = 99`, reads only the columns it tests instead of building every candidate node's row, in read queries and in writes alike. Results, row order, and errors are unchanged, including the error of a row past a `LIMIT`.
- Reading a relationship whose chunk of 32 records is longer than 1 KiB, as with a few properties or one short string per relationship, no longer reads the database file each time. The block cache now keeps long values whole beside its pages, within the same memory budget, so repeated reads of such relationships, traversals that read their properties, and scans such as `MATCH ()-[r]->() RETURN avg(r.weight)` take no file read or checksum once the chunk is cached. `DatabaseStats::cache_hits` and `cache_misses` now count these reads too. A scan that reads more than 1 MiB keeps the rest of what it reads only in free room of the cache, so a scan of more data than the cache holds, such as over long text properties, does not push out the pages and values that lookups and traversals keep reading.
- A `LIMIT` stops the clauses before it once it has its rows, so `MATCH (a)-[:R]->(b)-[:R]->(c) RETURN a, b, c LIMIT 10` and `MATCH (a) WITH a LIMIT 10` read only the matches they return instead of every match, and a match reads its start nodes one row group at a time instead of listing them all first. `EXISTS { ... }` stops at its first inner row. A `LIMIT` keeps reading when a later row could still raise an error, such as a division by zero, so every query returns the same rows and errors as before, and a write before a `LIMIT` still applies to every row. A query that stops early this way at the projection right after its match splits across threads by row group: workers take one row group at a time and stop together once the groups before them hold the rows the `LIMIT` keeps, so `MATCH (n:P) WHERE n.id > 990000 RETURN n.id LIMIT 10` searches on every thread, while a `LIMIT` that its first row groups fill starts no thread. It also stops early past arithmetic that cannot fail, such as `i % 2` where `UNWIND range(...)` or `count()` gives `i`, or `+`, `-`, `*`, and `/` where a float literal or parameter is an operand. Integer `+`, `-`, `*`, and negation of a variable, division or modulo by anything but an integer literal or parameter other than zero, division by `-1`, and arithmetic on a property, as in `n.score * 2.0`, still keep it reading, since they can fail on a later row.
- A streamed query no longer sets up its plan of clauses from scratch on every run and on every outer row of an `EXISTS` or `COUNT` subquery: what each variable holds is decided once per query plan, so point queries such as `MATCH (n) WHERE id(n) = 5 RETURN n.id LIMIT 1` and correlated subqueries cost less.
- `ORDER BY ... LIMIT k`, with or without `SKIP`, keeps only the `SKIP` plus `LIMIT` rows that rank first as rows arrive instead of holding and sorting every row, so `UNWIND range(1, 1000000) AS i RETURN i ORDER BY -i LIMIT 10` uses memory for 10 rows. The rows, their order among ties, and the errors are unchanged.
- `min()` and `max()`, with or without `DISTINCT`, keep one value per group as rows arrive instead of holding every value of the group until the end, so `MATCH (n:N) RETURN min(n.x), max(n.x)` uses memory per group instead of per row and no longer slows down when it splits across threads. The results are unchanged, ties between equivalent values such as `1` and `1.0` included.
- `percentileCont()` and `percentileDisc()` sort their values once instead of twice.
- Joining the `collect()` lists of a query split across threads checks the value limits once per list instead of once per item.
- The evaluator and the binder spend a fraction of the stack per level of nesting that they did, since each kind of expression and clause now runs in a frame of its own. A query nested to the parser's limit, such as `RETURN true` followed by 127 ` IS NOT TRUE`, now needs about half the stack that 0.1.0 needed in a release build, well inside the 1 MiB budget.
- A commit that range-deletes keys already in the database file no longer looks each of them up in the file again before it becomes visible, while it holds the writer lock.
- A quoted phrase in a keyword search decodes in full the postings of only its word with the fewest posting blocks, and of its other words only the blocks of 128 element IDs where that word's matches remain, so `"zebra the"` no longer reads every posting of `the`.

### Fixed

- A query or write transaction kept a copy of every property column and node meta chunk it read more than a few times until it ended, so a traversal over a large graph, as in `MATCH (a)-[:KNOWS]->(b) RETURN sum(size(b.bio))`, could hold a copy of most of the graph's column data. Each reader now holds a bounded number of bytes and drops what it used longest ago, and a column or chunk it dropped is read in place from then on. Adding an entry no longer shifts every entry after it when groups arrive in random order. A reader keeps four caches for property columns and two for node labels, each of at most about 8 MiB, and a write transaction has a reader for its own statements besides each query's. In exchange, a traversal that reads more column data in random group order than a reader holds reads most values in place and can run up to about twice as slow as before, while its peak memory drops three to five times. Scans and traversals whose columns fit do not slow down.
- A damaged relationship chunk read as data: a changed byte inside one could return other property values or relationships without an error. Each chunk now carries a CRC-32 of its key and contents, so reading, changing, or `Database::check` on a damaged chunk fails with `ErrorKind::CorruptData`.
- An aggregate after `UNWIND`, `CALL`, or `WITH`, as in `UNWIND range(1, 10000000) AS i RETURN count(*)`, held every input row before it grouped them and could use gigabytes of memory. It now keeps one state per group as rows arrive, and `UNWIND range(...)` gives its integers one at a time instead of building the list.
- A short query could still abort the host process by multiplying values that each stayed under the length caps, as in `[x IN range(1, 10000000) | range(1, 10000000)]`, `collect(range(1, 1000))` over many rows, or a `reduce` that appends a new list at every step. List comprehensions, pattern comprehensions, `COLLECT` subqueries, `collect()`, list and map literals, `CAST`, `split()`, `toUpper()`, `toLower()`, and `normalize()` now fail with `ErrorKind::NumberOutOfRange` once their value passes the limits, and the limits count the items and strings of nested lists and maps too, where 0.1.0 counted each list or string alone.
- A `reduce` whose body appends to its accumulator, as in `reduce(l = [], i IN range(1, 1000000) | l + i)` or the same with strings, copied the accumulator at every step and took time quadratic in its length. It now grows the accumulator in place.

### Known limitations

- The limitation of 0.1.0 still holds: an open that reads a header only the operating system's page cache held writes its clean header into the slot of the one durable header, and a power loss that tears that write loses acknowledged commits without an error.

## 0.1.0

The first release: an embedded, schemaless property graph database for Rust programs, queried with GQL.

### Added

#### Storage and durability

- One database file of RhizoDB's own storage engine, beside a write-ahead log that a clean close empties. Every page carries a checksum, so damage fails with `ErrorKind::CorruptData` where it is read.
- A commit returns once its log record is synced, and a crash or power loss keeps every acknowledged commit. Checkpoints write the log into the file in the background.
- An exclusive lock on the open file, on a file system with file locks, so a second `Database` on the same file, in this process or another, fails with `ErrorKind::DatabaseAlreadyOpen`.
- Nodes keep their labels as interned label sets and their properties in typed columns per property key, and relationships live in compressed adjacency segments, so scans, filters, aggregates, and label counts read only what they use.
- Automatic space reclaim: a file that holds much more than its live data is compacted after a checkpoint, so a long-running host's file does not grow without bound.
- `Database::in_memory` and `OpenOptions::in_memory` run the same engine in memory.

#### Query language

- GQL queries through `Database::execute`, with `MATCH`, `OPTIONAL MATCH`, `INSERT` (and Cypher `CREATE`), `SET`, `REMOVE`, `DELETE`, `DETACH DELETE`, `MERGE`, `UNWIND`, `WITH`, `FILTER`, `LET`, `NEXT`, `ORDER BY ... NULLS FIRST | LAST`, `UNION`, `EXCEPT`, `INTERSECT`, and `OTHERWISE`.
- Label expressions with `|`, `&`, `!`, `%`, and parentheses, every GQL edge orientation, `IS [NOT] LABELED`, and variable-length relationships in the Cypher form `-[:R*1..3]->`. GQL path quantifiers such as `->{1,3}` are not supported and fail as a syntax error.
- Subqueries: `EXISTS`, `COUNT`, `COLLECT`, and `VALUE { ... }`, and `CALL { ... }` with variable scope clauses, `OPTIONAL CALL`, and updating bodies.
- Values: null, booleans, integers, floats, strings, bytes, lists, maps, nodes, relationships, paths, and temporals (dates, times, datetimes with zones, and durations).
- Type predicates `IS [NOT] TYPED` and `IS [NOT] ::`, `CAST(value AS type)`, `valueType()`, `normalize()` and `IS [NOT] NORMALIZED`, `IS [NOT] TRUE | FALSE | UNKNOWN`, and `IS [NOT] DISTINCT FROM`.
- The GQL string, numeric, list, and temporal functions, regular expressions with `=~`, `reduce()`, and `vector.similarity.cosine` and `vector.similarity.euclidean`.
- Host-registered procedures with `Database::register_procedure`, called with `CALL` outside the `db` namespace that built-in procedures reserve.

#### Transactions

- Every query runs in its own transaction, and `Database::begin_read` and `Database::begin_write` open explicit ones: snapshot reads, and one writer at a time.
- Read queries that match from many start nodes split them across threads, set with `OpenOptions::threads` and `OpenOptions::parallel_threshold`, and return the same rows in the same order as on one thread.

#### Indexes

- Keyword (BM25) indexes with `"quoted phrases"` and `prefix*` terms and text compared in Unicode normalization form NFKC. Text without spaces between words, such as Hangul, Han, Hiragana, Katakana, Thai, Lao, Khmer, and Myanmar, is indexed as overlapping pairs of characters, since no word dictionary splits it.
- Exact vector indexes with cosine, euclidean, and dot product metrics.
- Property indexes over one property, which `MATCH` and `MERGE` read for `=`, `IN`, `<`, `<=`, `>`, and `>=`.
- Indexes are created and dropped through `Database::create_keyword_index`, `Database::create_vector_index`, `Database::create_property_index`, and `Database::drop_index`, which take an `IndexTarget` and, for vectors, a `VectorMetric`. GQL has no index statements.
- Every index covers the nodes of a label or the relationships of a type, changes in the same transaction as the data it covers, and is searched with `CALL db.index.keyword.queryNodes`, `queryRelationships`, and their `db.index.vector` counterparts.

#### Operations

- Online backups with `Database::backup_to`, which copy one snapshot into a new file while readers and writers carry on and never leave a partial file. Restoring a backup is opening it.
- Logical dumps with `Database::export` and `Database::import`, a versioned JSON Lines format that keeps IDs, labels, index definitions, and every value's exact type.
- `Database::compact`, `Database::stats`, and `Database::check` for giving space back, reading the file's size, live data, log, and cache counts, and checking every page.

#### API

- `Database`, `OpenOptions`, `DatabaseStats`, `ReadTransaction`, `WriteTransaction`, `QueryResult`, `Value`, `Node`, `Relationship`, `Path`, `NodeId`, `RelationshipId`, `Parameters`, `IndexTarget`, `VectorMetric`, `Procedure`, `ProcedureOutput`, `ProcedureError`, `ValueType`, and the temporal types.
- `Error` with `Error::kind` for a stable `ErrorKind`, and `Error::byte_offset` and `SyntaxErrorKind` for where and why the parser refused a query.
- `Display` for `Value`, `Node`, `Relationship`, and `Path` as GQL literals, so a host can print query results without writing a formatter.
- `Value`, `Temporal`, `ErrorKind`, `SyntaxErrorKind`, `ValueType`, and `DatabaseStats` are `#[non_exhaustive]`, so later releases can add to them, and `WriteTransaction` stays on the thread that began it.
- The minimum supported Rust version is 1.100.

### Notes

- A database file written by a pre-release build opens only if its graph format is 11 or later, and an older one fails with `ErrorKind::UnsupportedFormatVersion`. Files this release writes use engine format 1.3, which earlier pre-release builds refuse.
- An open that finds the file lock held tries again for about half a second before it fails with `ErrorKind::DatabaseAlreadyOpen`, since a child process the host spawns shares the lock until it starts its program.
- `OpenOptions::create(false)` refuses a missing or empty file with `ErrorKind::DatabaseNotFound`, and leaves an empty file as it was.
- `Database::import` makes write transactions on other threads wait until it ends.
- The first open after a change of the keyword tokenizer, such as a dependency update that brings new Unicode tables, rebuilds every keyword index in that open.

### Known limitations

- An open that reads a header only the operating system's page cache held, as after a failed fsync or a process that stopped before its header was synced, writes its clean header into the slot of the one durable header. A power loss that tears that write falls back to an older header and loses acknowledged commits without an error.
