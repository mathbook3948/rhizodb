# Storage engine

Decides the design of RhizoDB's own storage engine, which stores every database.

## Background

An off-the-shelf B-tree store sets a floor under the cost of a put, the growth of the file, and its size, and no change to the graph layout removes it. RhizoDB therefore has its own engine behind the storage trait, and leaves room for replication and for spreading data over several disks and servers.

## Decisions

- RhizoDB's own engine is the only storage backend of `Database`, on disk and in memory.
- The engine is a module of the `rhizodb` crate.
- The engine implements the storage trait, and the graph layer reaches it only through that trait.
- A database at rest is one file.
- The engine holds an exclusive lock on the database file while it is open, so a second open of a database fails in any process until the first closes it.
- A read-only open takes a shared lock on the database file instead, so any number of read-only opens hold the file at once and each keeps out every open that writes.
- An open that finds the lock held tries again for half a second before it fails, since a child process the host spawns shares the lock until it starts its program.
- The simulated file system enforces locks as Windows does, so an exclusive lock keeps other handles from reading or writing the file, and a shared lock keeps every handle from writing it.
- A read-only open opens every file without write access, and never creates, writes, renames, or removes a file, not even a staging file or a leftover segment.
- A read-only open of a missing or empty file fails instead of creating a database.
- A read-only open takes the standard library's whole-file shared lock, and only then fails with `DatabaseAlreadyOpen` when a `-shm` side file lies beside the database file, so it never reads a file that a multi-process session of a later build holds.
- A read-only open detects a multi-process session only by its `-shm` file, so the session's first process must create that file while it holds the exclusive lock, and a session whose last process leaves the file behind keeps every read-only open refused until the file is removed.
- A read-only open of a cleanly closed database reads no log, and one after an unclean shutdown replays the log into memory and leaves a torn tail and an unfinished last segment on disk.
- A read-only open syncs every segment it replayed, and their names, before any reader sees a replayed commit, since a writer that died between an append and its sync left a record that only the page cache holds and a power loss would take back.
- Syncing the segment names on replay is defense in depth, since a writer syncs the directory as it creates a segment, so the names are durable already unless that writer died in between.
- On Windows a read-only open of a database that was not closed cleanly fails with `ReadOnly`, since only a handle with write access can flush a file there and a read-only open opens none.
- A process holds at most one read-only open of a file, keyed by its canonical path, since shared locks of one process never conflict and the multi-process design lets a process open a file once.
- A read-only open reads a file of an older engine minor as it is, since every minor this build reads needs no rewrite to be read.
- A read-only open of a file whose graph format or tokenizer needs an upgrade fails with `ReadOnly`, since the graph reads only its current layout and the upgrade is a write.
- A read-only database refuses every write, checkpoint, compaction, and change to its replication state or the log it keeps for peers with `ReadOnly`, and starts no checkpoint thread.
- A read-only database reports through `Database::role` the role an open that writes would find in the file, such as `Writer` for a file without a replication history, though it refuses every write.
- A snapshot of a read-only database whose last checkpoint a crash cut between its stages fails with `ReadOnly`, since only an open that writes finishes that checkpoint.
- On a file system without locks the engine opens a database unlocked.
- An open that asks for multi-process access replaces the exclusive lock with the session locks that `multi-process.md` decides.
- In such a session a checkpoint reuses no block that a tree in any process reaches, as `multi-process.md` decides.
- In such a session the process that writes a header removes the log segments it released, as `multi-process.md` decides.
- In such a session only the last process to close checkpoints the whole log and removes its segments, as `multi-process.md` decides.
- Opening an empty file with no log segments creates a new database in its place.
- The write-ahead log is a separate log made of segment files next to the database file.
- An open resolves the database path once, following every symlink and `..`, and finds the segments and the staging file beside the file it reaches, under that file's name, so every path to one file finds the same log.
- An open through a symlink whose target does not exist creates the database file at the target and keeps the symlink.
- An open on Unix refuses a database file with more than one hard link, since each name would find its own log.
- An open that is not read-only moves segments that a release before the fix named after the symlink it was given, beside that symlink, to the file, when the log beside the file is missing or exactly continues the moved segments.
- The move holds the file's lock, is refused where the file system has no locks, and first replays the moved segments with the file's own log as a read-only open, moving nothing and naming the segment files when that fails.
- The move renames the newest segment first and syncs both directories after each, so a crash mid-move leaves the file without the start of its log, which an open through any other path refuses, and the next open through the symlink finishes.
- Only the path the crashed process was given finds such segments, not the real path or another link in a chain of symlinks.
- An open refuses, and changes no file, when the segments beside the file do not exactly continue the ones beside the symlink, and a read-only open refuses wherever the move is due.
- On Windows resolving a path needs `GetFinalPathNameByHandle`, so a volume without it cannot hold a database, and paths in messages may take the `\\?\` form.
- A WAL record is a logical key-value operation, the put of a value under a key of a table or the delete of a key.
- A range delete of the storage trait is logged as one operation of its batch.
- Every WAL record carries a log sequence number (LSN) and a checksum of its own.
- Each WAL segment starts with a header holding the database id, the segment number, and the segment's first LSN.
- A WAL segment can be shipped to another node and replayed there on its own.
- A commit returns only after its WAL records are durable.
- A checkpoint writes the committed WAL records into the database file.
- Checkpoints run on a background thread by default, and an inline mode runs them on the committing thread for deterministic tests.
- A clean close checkpoints the whole WAL and removes its segments.
- Opening a database that has WAL segments replays them before any transaction begins.
- After a crash, the database holds a prefix of the commits that includes every acknowledged commit.
- A failed fsync makes the engine refuse every later commit until the database is reopened.
- The engine does all I/O through a file-access trait that reads and writes whole fixed-size blocks by block number, never arbitrary byte ranges.
- Each file has one block size, chosen when it is created.
- A layer over several files or devices, such as a mirror, a stripe, or parity, can implement the file-access trait without the engine knowing.
- Every page the engine writes carries a checksum and the LSN that last wrote it.
- A checksum mismatch is reported as corruption, never returned as data.
- The file-access trait has an implementation over the operating system's files, one in memory, and a simulated file system for fault tests.
- A database in memory runs the same engine over the in-memory implementation.
- The simulated file system is deterministic for a given seed.
- The simulated file system holds several files and can inject faults into one of them alone.
- A simulated crash keeps every synced write and may drop, reorder, or tear at 512-byte sectors each write since the last sync.
- A write torn with garbage may also garble the other sectors of its 4 KiB unit, synced ones included, as a device that rewrites a whole page or sector does.
- A simulated crash may lose a change of file length, a create, a rename, or a remove that was not synced.
- The simulated file system can fail every operation after a chosen count, once or from then on.
- A failed fsync of a file in the simulated file system leaves the writes since the last sync to land, tear, or vanish at a crash, and no later fsync makes them durable, as Linux marks the pages of a failed writeback clean.
- A failed sync of the simulated file system's names fails every later one.
- The copy is closed cleanly before the rename, so the renamed file needs no log.
- `OpenOptions` holds no engine setting but the log it keeps for peers, so the engine's tuning stays internal.
- `Database` gains `compact`, `stats`, and `check`, and they are its whole maintenance API.
- Maintenance on the thread that holds the write transaction fails instead of waiting for itself.
- `stats` reports the file's bytes and live bytes, its live and free extents, the log's bytes, and the block cache's hits and misses since the open.
- `check` checks the file as its last checkpoint left it, and the commits after that checkpoint are checked as the log replays them.
- Each block cache shard counts its hits and misses beside its lock, so counting adds no shared cache line to a read.
- A vector index may read its vectors from the property column instead of keeping a copy.
- Every engine checksum is a 64-bit xxh3 hash, from the MIT-licensed twox-hash crate.
- The database file is made of 4096-byte blocks.
- Blocks 0 and 1 of the database file are two header slots, written in turn, and the valid slot of the higher generation describes the database.
- A header slot of a generation of the other slot's parity is invalid.
- A header slot whose generation, LSNs, first log segment, or extent counter is 2^63 or more is invalid, so no increment of one overflows.
- A header slot of another major engine format, a newer minor one, or with an unknown flag refuses the file instead of falling back to the other slot.
- An extent is 1024 blocks, and extent slot n starts at block 2 + 1024 n.
- A block reference holds the extent id in its high 44 bits and the block inside the extent in its low 20, and zero refers to nothing.
- Extent ids are never reused, and a block that a durable header reaches is never written again.
- Each of the four open extents in the header records its slot along with its id and written length, so the catalog can be read before the extent table.
- Every page records the block it was written to, and a page read from another block is corruption.
- Page checksums are seeded with the database id, so a page copied from another database is corruption.
- Tables have stable numeric ids, with 1 to 255 for the engine, 256 to 511 for the graph's tables, and the rest reserved.
- Log segments are files named after the database file with `-wal-` and the segment number in 16 hex digits.
- Log segments are made of 512-byte blocks, and the header and each record start a 4 KiB unit of their own, so an append never rewrites a page or a 4 KiB device sector that holds synced data.
- A segment header of engine format minor 3 or later records the 4 KiB unit its records start at, and a segment of an earlier minor, whose records start at 512-byte blocks, replays and takes appends at those blocks.
- A segment grows in steps of 1 MiB of synced zeros, up to the segment target, so an append writes into allocated blocks instead of growing the file.
- A record's checksum is seeded with the log's salt and the segment number, so a record of an older log or of another segment never passes.
- A record of a reserved kind, of an unknown body format, or holding the reserved patch operation refuses the log instead of being skipped.
- Recovery cuts off an invalid tail of the last segment, removes a last segment with an invalid header as an unfinished rollover, and reports damage anywhere else in the log as corruption.
- Damage in the last segment followed by a record that passes its checksum is corruption, since every append is synced before the next one starts, and so is a damaged header of a last segment that holds such a record.
- Recovery looks for such a record only where the LSN field holds an LSN a record there could carry, and hashes nothing else, so a torn tail of random bytes is scanned in linear time.
- A log that ends before the checkpoint's LSN is corruption.
- A segment longer than the segment target and longer than a header and the longest record is corruption, refused before recovery reads it.
- Segments wholly before the checkpoint are removed, not reused.
- The database file is created under a staging name and renamed into place once its header is synced.
- Opens that race to create a database take turns through a lock on the staging file, so exactly one of them creates the database and the others find that database.
- Opening reuses a staging file left by an interrupted open, and removes one found next to an existing database.
- On Windows, a staging file that another open is removing refuses access until it is gone, so an open that meets a refusal of access at any step of creating the database waits and tries again as it does for a locked staging file.
- Opening a cleanly closed database starts a log with a new salt, which a header without the clean flag records before any commit, and removes leftover segments once that header is durable.
- Opening a database after an unclean shutdown writes every replayed commit into the file under a clean header and then starts a new log as for a cleanly closed database, so no commit rests on log records or a header that only the page cache held, and a power loss before that header is durable leaves the old log as it was.
- That checkpoint places nothing in free blocks or free slots and cuts nothing off the file, since the header the open read may be one only the page cache held, and the older header in the other slot may still reach those blocks.
- The open compacts the file only once the new log's header is durable, since a compaction that cannot reuse free space only grows the file.
- A database in memory keeps its log on the in-memory file system too.
- A read reaches its snapshot's layers newest first: the memtable commits go to, the memtable a checkpoint is writing out, and the tree of the last checkpoint.
- The memtable keeps each key's versions tagged by LSN, and a reader sees the newest version at or below its snapshot.
- Every reader registers its snapshot, and a commit drops each version that no registered snapshot or later one can see.
- A commit's tombstone of a key that neither the frozen memtable nor the tree holds is dropped with its key's versions once every registered snapshot sees the commit.
- A range delete remembers which keys it found below the active memtable, so its commit looks up only the rest to find tombstones that hide nothing.
- A write transaction keeps its operations in order, for the log, and each written key's value now, for its own reads and for the memtable.
- A scan copies memtable entries out in batches that grow as it reads, each under its own read lock, so a scan that stops early copies about as many entries as it read, and no lock is held while the caller handles an entry.
- A range delete puts a tombstone in the memtable for each key it removes, and replaying its log operation finds the same keys.
- A commit's record is synced to the log before its versions join the memtable and the commit becomes visible.
- A commit's timestamp is the wall clock in microseconds, or one past the previous commit's when the clock has not moved past it.
- A replayed operation on a table id this build does not know refuses the log.
- The database file is copy-on-write: a checkpoint writes each changed page and run to a block that neither a durable header nor an open snapshot reaches, never in place.
- Each table is a copy-on-write B+tree of one-block pages, and a checkpoint writes the leaves it changes and their paths as new pages.
- A child pointer holds the child's block reference and LSN, and a child of another LSN, kind, level, or table is corruption.
- A page shares the common prefix of its keys, capped at 512 bytes, and stores each key's rest.
- A cell stores its key before its value or child pointer, and a search compares the page prefix once and then the stored rests.
- A leaf whose keys and values all have one width uses a fixed format without per-cell offsets, which stores every key before every value, so a search reads only the cache lines that hold keys.
- A fixed leaf of engine format minor 0 stores each key beside its value, and every later minor still reads it.
- Every header a checkpoint writes records this build's minor, so an older build refuses a file that holds pages it cannot read.
- A branch stores the lowest key of each child but the first, chosen as the shortest key that separates two leaves.
- A value longer than 1 KiB lives in a run of blocks inside one extent, and its cell holds the run's reference, block count, LSN, the value's length, and its checksum.
- A scan reads a value's run only for a caller that asks for the value, and gives the value's length to one that does not.
- A key longer than 1 KiB lives in a run too, and its cell keeps its first 64 bytes after the page prefix, so most comparisons read no run.
- An item larger than an extent is a chain of runs, each naming the next run and the slot of its extent.
- A chained item is placed from its last run to its first, so the first run of a catalog lies in an open extent the header names.
- A run's header names its table, its role, and the first bytes, length, and hash of the key it belongs to.
- Each page owns the runs of its long keys, which are rewritten with it, while a value's run stays until its entry changes.
- A checkpoint packs cells greedily on the rightmost path of a table, so appends leave full pages, and spreads cells evenly elsewhere.
- A short page joined with its neighbour is packed greedily too when the pair ends the rightmost path, so an append that leaves a short last page splits no full page in two.
- A rewritten page under a quarter full is merged with a sibling, and a root with one child gives way to that child until the root has several children or is a leaf.
- Every page and run a checkpoint writes carries the checkpoint's LSN and header generation.
- The catalog holds every table's root, height, and entry count, and the whole extent table, written as a run at each checkpoint.
- The extent table records each extent's slot, written and live blocks, state, and purpose, and keeps room for a replication scheme and the term that opened it.
- A checkpoint appends tree pages, runs of keys and values, and the catalog to one open extent, so a file ends after its live blocks instead of after a mostly empty extent for each kind of block.
- A block goes to the first open extent with room for it, and when none has room, every open extent is sealed and one new extent is opened.
- A file of engine format minor 1 may hold an open extent for each kind of block, and checkpoints fill the room left in each of them before the first new extent.
- Every new extent is recorded with the tree purpose as the first open extent, so the layout needs no new format minor and an earlier build still reads and writes the file.
- Extents stay 1024 blocks at every file size, since the space a small file lost was the empty room of one open extent per kind of block.
- The extent table records which blocks of each extent hold a live page or run, stored as the free ranges below its written length.
- A checkpoint places each page and run in the first free range that fits it in the lowest slot, and appends to the open extent only when no free range fits.
- A block freed by a checkpoint takes a new page only in a later checkpoint and only once no reader holds a tree older than the one that freed it, as a freed slot does.
- The catalog goes only to an open extent, in a free range or at its end, so its first run always lies in an open extent the header names.
- A checkpoint seals the open extent and opens one in the lowest free slot when that slot lies below it, so the slots above it can empty and be cut off the file.
- A checkpoint with no commits to write still writes a new catalog when that moves the open extent down, and a clean close runs one more such checkpoint, so a file that has emptied its last extents shrinks before it closes.
- Writing a block removes the page or value the block cache held for it, so a reused block never reads back its old page or value.
- The block cache keys a long value, and writing removes it, by its chain's first block alone, since a block of a later run is written again only once no tree reaches the chain, so no tree can still look up a pointer to it.
- A compaction places nothing in free ranges, so its first copy empties every old extent and its second fills the lowest free slots.
- Opening a file of engine format minor 1, whose catalog counts each extent's live blocks without naming them, finds them by walking every tree, and the first checkpoint stores them.
- A checkpoint drops every sealed extent left with no live block from the extent table, and its slot becomes free.
- A free slot takes a new extent only in a later checkpoint and only once no reader holds a tree older than the one that dropped it, so neither a durable header nor a snapshot loses a page.
- An extent in a reused slot has a new id, so a page left there by the extent before it fails as written for another block.
- A checkpoint cuts the file after the last written block of the last extent in use when the slots after it are free and unread, both before it writes and once its header is durable.
- An open drops the free slots after the last extent in use from the extent table, so the work of finding free slots grows with the file and not with a count a damaged catalog records, and an extent that starts past the end of the file fails the open as corrupt data.
- `compact` writes every commit into the file, then copies every table into new full pages twice, so the first copy empties every old extent and the second fills the lowest free slots.
- After each checkpoint, a clean close's included, the engine compacts the file when it holds more than twice its live data plus one extent, and has grown by its live data since the last compaction, so a file that has lost most of its data gives the space back by the time it closes.
- A clean close that compacted writes one more clean header, so the file it leaves needs no log.
- The extent in that bound is the room of the open extent, which a compaction cannot give back, so a small file that compaction cannot shrink is not compacted at every open.
- An automatic compaction runs where the checkpoint ran, on the background thread or inline, and a failed one poisons the engine like a failed checkpoint.
- An automatic compaction waits while a snapshot or a write holds a tree older than the durable one, since its second copy could reuse no slot its first copy empties, and the background thread starts it once those trees are gone, while inline checkpoints try again at the next checkpoint.
- A commit holds no tree of its own while it starts a checkpoint, so an inline compaction can reuse every slot it empties.
- A checkpoint freezes the memtable under the writer lock, writes the frozen versions into the file, syncs it, and writes and syncs the other header slot.
- A checkpoint makes its work durable in stages: once a stage has freed an eighth of the file's live blocks, and at least 256, it syncs the file and writes a header, so the next stage reuses the blocks it freed and a rewrite of most of the file does not double it.
- A table's changes are cut into parts of at most a stage's blocks, in keys and in bytes, only when its tree already holds entries, so a load into empty tables writes no extra pages.
- A stage's header keeps the LSN the log replays from and records the LSN its tree holds, and a crash after it replays the log over that tree, which ends in the same state since every logged operation sets or removes its keys outright.
- Each stage publishes its tree, so a reader that begins during a staged checkpoint reads the frozen memtable over the newest stage.
- Commits go on into a new memtable while a background checkpoint or compaction runs, and a commit waits for it once the new memtable reaches twice the limit.
- A checkpoint starts when the memtable passes 64 MiB or the log passes 256 MiB.
- Log segments before the one that holds the checkpoint's next LSN are removed after the header that no longer needs them is durable.
- With background checkpoints, the writer only drops those segments from the log's list and the checkpoint thread removes their files, so no commit waits for the removal.
- A segment file that fails to be removed, or is already gone, poisons nothing, since no durable header needs it, and the next open removes it.
- The background checkpoint thread keeps each memtable it wrote until no snapshot holds it and frees it then, so no commit or reader frees a frozen memtable.
- A failed checkpoint poisons the engine and leaves the frozen memtable serving reads, and later writes fail as corrupt data when the checkpoint failed on damaged data.
- A commit publishes only its LSN, and only a freeze under the writer lock replaces the memtable that commits go to.
- The block cache is a sharded CLOCK of checked pages keyed by block reference, and the engine maps no file into memory.
- A new block cache entry takes the first place the hand freed for it, behind the hand, so it waits a whole turn of the hand for its first use, and a new working set takes the place of one no longer read.
- The block cache also holds each long value a read loaded from its runs, whole and checked, under its first run's block, and serves it only to a cell whose pointer matches the one it was loaded for, so reading the value again reads no file and checks no checksum.
- Pages and values share one budget of the block cache in bytes, a page counting its block and its checked header, a value its length, and each entry also its map slot, clock place, and reference counts, and a value longer than a quarter of a shard's budget is not kept, so one large value never empties a shard.
- A scan reads its first MiB of pages, and apart from them its first MiB of long values, as lookups do, and keeps what it reads after that only in free room of the block cache, so a scan longer than the cache pushes out at most those first MiB of entries the hand finds unused, and a scan whose data fits the free room is served from the cache the next time.
- `check` and the copies of `compact` read values from the file without the cache, so a check reads what the file holds and a compaction does not push hot pages out.
- Each tree pins the root page of every table it holds and, once read, each page a root points to, so no read takes the block cache or a reference count for the top two levels.
- Each memtable keeps a blocked Bloom filter of its keys, so a read of a key the memtable lacks takes neither its lock nor its search.
- The memtable orders keys by their first 16 bytes held beside the key, so most comparisons read no key bytes.
- Every test of `Database` and of the graph layer runs on the engine.
- `check` walks every tree from the durable header and compares key order, key ranges, entry counts, and each extent's live blocks with what it reaches.
- `check` takes the durable header, extent table, catalog, and tree, then walks them without the lock that checkpoints take, and the tree it holds keeps its blocks from reuse until it ends.

## Open

- How the engine's reader registration, commit, freeze, checkpoint, and slot reuse are explored across thread interleavings, beyond the randomized tests that run them on real threads.
- How a cleaner moves the live blocks of partly live extents without copying the whole file, so an automatic compaction does not stall writers of a large database.
- How a write set larger than the memtable is ingested.
- How a scan warms a block cache full of entries nobody reads any more, since a scan read past its first MiB evicts nothing, not even an entry whose used flag is clear.
- How the extent table is written when rewriting it whole at every checkpoint costs too much.
- How a point read that overlaps a background checkpoint keeps its speed, since the checkpoint's memory traffic slows it.
- Where extents are placed across files, disks, and servers.
- How data is replicated, erasure-coded, and partitioned across servers.
- How an open makes a header that only the page cache held durable without risking the one durable header, since the open's clean header goes to that header's slot, and a torn write there falls back to an older header and loses acknowledged commits without an error.
